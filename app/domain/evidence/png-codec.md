# PNG codec boundary evidence (issue #25, part of #5)

Date: 2026-09-17. Scope: `app/domain/src/png.rs` (`encode_png` /
`decode_png`), `app/domain/tests/png_codec.rs`, and
`app/domain/tests/fixtures/png/`.

**Evidence category: software fixture evidence.** Independent third-party
encoders/decoders were used to generate and validate fixtures, and every
claim below comes from executed tool output. There is no device hardware
involved, no optical-bench measurement, and **no JPEG** — JPEG encode/
decode remains out of scope and unstarted.

## What was implemented

- `encode_png(&GrayFrame) -> Vec<u8>`: deterministic 8-bit non-interlaced
  grayscale PNG (color type 0). Scanlines use filter 0 (None); pixel data
  is wrapped in a zlib stream of deflate *stored* blocks (no compression).
  Output for the 5x4 sample frame is 92 bytes (raw 20 + framing), which is
  the accepted trade: the encoder side optimizes for provable correctness,
  and the export layer's 64 MiB bound is the real size constraint.
- `decode_png(&[u8]) -> GrayFrame`: baseline subset — 8-bit, non-interlaced,
  color type 0. Accepts all five PNG scanline filters (None/Sub/Up/
  Average/Paeth), all three deflate block types (stored, fixed Huffman,
  dynamic Huffman), and multiple IDAT chunks. Rejects color types
  2/3/4/6, non-8 bit depths, interlacing, and PLTE/tRNS/unknown-critical
  chunks with stable `DomainError::InvalidRequest`; rejects CRC/Adler
  failures with `ChecksumMismatch`.
- Bounded-input discipline before allocation: IHDR dimensions pass the
  crate's shared `check_bounds` (`MAX_DIMENSION_PX`, `MAX_FRAME_PIXELS`)
  *before* decompression starts; the inflate destination is fixed at
  `height * (width + 1)` bytes from IHDR and never grows with stream
  content; total IDAT bytes are capped at `MAX_CAPTURE_BYTES` (64 MiB);
  output overrun ends the decode as an error, not a panic.

## Decoder cross-validation (independent encoder side)

Fixtures in `tests/fixtures/png/` were generated by `generate.py` using
encoders that share no code with the Rust crate, then validated with
Pillow (libpng + zlib) *at generation time* — the script asserts
Pillow's decode matches the source pixels byte-for-byte for every valid
fixture and that every reject fixture really carries the claimed
property (bit depth 16, Adam7 interlace, RGB color type, PLTE presence).

| Fixture | Independent encoder | Covers |
|---|---|---|
| `pil_noise_32x32_seed7.png`, `pil_flat_5x5.png`, `pil_gradient_17x5.png`, `pil_1x1_{white,black}.png` | libpng via Pillow (dynamic Huffman, filter 0) | normal-path decode, multi-kibble IDAT, 1x1 boundary |
| `pil_noise_1x40_seed3.png`, `pil_noise_40x1_seed4.png` | libpng via Pillow | 1-pixel-wide/tall edge geometries |
| `crafted_filters_11x9.png` | Python `zlib` + hand-built chunk/framing | scanline filters 1–4 (libpng's default encoder never emits these; Pillow validated the result) |
| `crafted_fixed_block_6x6.png` | hand-built fixed-Huffman block + Python zlib | fixed-Huffman block type (neither libpng defaults nor our encoder ever emit it; zlib validated the stream, Pillow the PNG) |
| `rust_encoded_sample_5x4.png` | **this crate's** encoder | pinned byte-for-byte; Pillow decoded and matched pixels at generation time |

Reject fixtures (independently produced, Pillow-confirmed property,
Rust decoder must reject without panicking):

| Fixture | Produced by | Property |
|---|---|---|
| `rgb_4x4.png` | Pillow | color type 2 |
| `palette_4x4.png` | Pillow | color type 3 + PLTE |
| `gray16_4x4.png` | Pillow | bit depth 16 |
| `interlaced_8x8.png` | pypng (pure Python) | Adam7 (Pillow/libpng decodes it; our subset rejects it) |
| `truncated_idat.png` | byte truncation of a PIL file | chunk CRC/truncation path (Pillow also rejects it) |

The Rust test `third_party_encoded_fixtures_decode_to_expected_frames`
decodes each valid fixture and compares `GrayFrame::digest()` to the
manifest digest computed in `generate.py` by a *separate* SHA-256 over
`"foldscan.frame/1" || width_le32 || height_le32 || pixels` (matching the
Rust `digest()` construction). It cannot pass unless the Rust decoder
agrees with the independent encoder + independent decoder + the manifest's
pixel model on every byte.

`unsupported_format_fixtures_are_rejected_without_panics` wraps each
reject fixture in `catch_unwind` — a panic on hostile input is a test
failure, not a crash to triage later.

## Encoder cross-validation (independent decoder side)

`rust_encoded_sample_5x4.png` (92 bytes) is committed. `generate.py`
recorded its Pillow-decoded pixels and digest in `manifest.json`;
`encoder_output_is_byte_stable_against_pillow_validated_sample` asserts
today's encoder emits those exact bytes, so any drift in framing, CRC
polynomials, stored-block wrapping, or filter bytes that would change
users' stored derivative digests fails CI.

## Multi-IDAT

`idat_split_across_chunks_decodes` re-wraps our single IDAT into three
correctly-CRC'd chunks (legal and common for libpng output) and requires
identical decode — the concatenation path across chunk boundaries is
exercised, not just assumed.

## Fuzz-style robustness note

Not performed: an actual fuzzing campaign (no fuzz harness in the repo
CI). The malformed-input coverage is the curated reject fixtures plus the
unit tests listed below. A fuzzer over `decode_png` remains a reasonable
future slice; the bounded-allocation design (fixed destination from IHDR,
IDAT cap, no allocation scaling with stream content) is the structural
mitigation a fuzzer would probe.

## Known gaps

- JPEG: untouched (explicit non-goal). Device captures are `image/jpeg`
  per the protocol; a decoder for those needs its own slice and the
  licensing/size evaluation app/README defers.
- Interlaced, palette, 16-bit, and alpha PNGs are *rejected*, not
  supported. The export default ("omitted media type means PNG") is
  satisfied by the grayscale subset our own encoder emits; reading
  arbitrary third-party PNGs is out of scope.
- No dedicated fuzz harness (see fuzz-style robustness note above).
- The encoder's stored-block strategy is ~50% larger than a Huffman
  encoder on compressible pages; revisit if derivative size matters
  before the PDF/UI layers make it painful to change.
- Physical captures from an actual device have never been decoded —
  hardware/firmware (#1/#2/#4) don't exist yet, so real-capture decode
  evidence is structurally impossible today and must not be claimed.
