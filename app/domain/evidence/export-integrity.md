# Export plan/manifest consistency — issue #19

Date: 2026-09-14. Base revision: `363014d95688712d8403eeeba43226de56449271`.
Issue: https://github.com/rwrife/foldscan/issues/19 (bounded follow-up under #5).

## Defect and change

`ExportPlan` and `ExportManifest` are independently mutable public structs.
The previous executor validated manifest shape and session ID, but not whether
its content matched the export plan. It also trusted a caller-edited file list
provided exactly one manifest entry appeared last.

The executor now regenerates the canonical layout from the plan's sessions and
recipes, compares every ordered file entry, derives the expected manifest, and
compares the complete manifest document. Mismatches return `invalid_request`
before creating either the export root or its parent directories. This protects
page membership/order, original/derivative paths, byte counts, checksums, recipe
linkage, file kinds, capture associations, and manifest-last layout. A writer
must use the canonical schema generated by `ExportManifest::from_plan` (currently
`foldscan.export/0.1`); parsing behavior for existing manifests is unchanged.

## Evidence category and limitations

Real Rust compilation/linting and local filesystem tests using synthetic data.
The fixture's JPEG-like originals and raw grayscale derivative bytes are not
image codec validation. No device, optical bench, UI, PDF, OCR, or physical
power-loss experiment is represented.

The check establishes internal consistency at the executor boundary, not
independent authenticity of caller-provided sessions or approval by a user.
Single-session export and existing filesystem durability/security assumptions
remain unchanged: no parent-directory fsync, no new protection against another
process concurrently modifying the export tree, and no new cleanup-failure
recovery mechanism. Broader desktop acceptance criteria remain open under #5.
No KiCad/BOM/datasheet/firmware/mechanical files changed, so their hardware
checks are not applicable to this software-only fix. CI results are recorded in
the associated PR rather than represented as local execution.
